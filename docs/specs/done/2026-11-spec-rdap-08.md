# Spec 8: RDAP for netblocks and registrants

## Goal

The netblocks registered to an input organisation are found in each regional registry that offers
organisation search, not just RIPE's, and the registrants of in-scope addresses are recorded as
structured data so related organisations surface as candidates. Nothing found this way enters
scope on its own.

## Behaviours

1. An `rdap` stage, available under `--passive`, contacts only IANA and the five regional
   registries. Lookups by address use the IANA bootstrap to choose the registry; organisation
   searches go to every registry that supports them, which the README lists. A lookup the registry
   refers to a server outside those six completes with no data and a `--verbose` warning naming
   the address.
2. For each `--org` input, netblocks and autonomous systems returned are recorded as candidates
   in `candidates.csv` with source `rdap`; the user passes one as `--cidr` or `--asn` to bring it
   into scope. A result is kept only when its registrant name contains every word of the `--org`
   name, ignoring legal suffixes (the same rule as the existing org pivot), up to 50 per registry;
   a truncated result produces a `--verbose` warning. A registry without search support completes
   with no results and a `--verbose` note.
3. For each recorded address that is port-eligible or inside an in-scope netblock, is not shared
   provider infrastructure and is not inside an input or ASN-expanded netblock, one lookup
   records the registered netblock, the registrant name and the registry. Addresses inside a
   registered netblock already looked up reuse that answer. `ips.csv` keeps the announcing
   network's `owner` and adds `registrant`, `registrant_netblock` and `registry` columns.
4. A registrant seen on three or more distinct registered netblocks, whose addresses nyx does
   not classify as shared provider infrastructure, and whose name does not match an input `--org`
   by the rule in behaviour 2, appears in `candidates.csv` as a candidate of type `organisation`
   with the netblock count as its evidence. `candidates.csv` gains the `organisation` and `asn`
   types.
5. A 429 from any registry stops the stage for this run, as for other quota-limited sources; the
   remaining checks are retried next run.
6. Each lookup is made once per engagement and refreshed only by `--redo rdap`. The bootstrap
   file is fetched once per run.

# Design

**Status:** ready to build (wave 2). Specs 1 and 15 have merged. On 2026-11-14 the candidate
decisions below were rewritten against `internal/candidates`, `kinds.CandidateKinds` and the
`candidate-rank` deriver as built: the earlier design named a `candidate_asn` kind and derived
organisation candidates on read, and neither would have been ranked or listed. **Depends on:**
Spec 1 (`ErrQuota`, `Warnf`), Spec 15 (candidate model, `internal/orgname`).

## Decisions

- **One stage, `rdap`**, in `internal/stages/rdap`, with sources `data.iana.org` and the five
  registry RDAP hosts. A request anywhere else is impossible (egress checks `Sources()`).
- **Bootstrap once per run**: the stage fetches `ipv4.json` and `ipv6.json` lazily through
  `sync.OnceValues` on its first check; a failure fails the checks of this run and they are
  retried on the next.
- **Referrals are followed by hand** (the third-party client never follows redirects): a
  `Location` on one of the six hosts is requested, up to three hops; any other host completes the
  check with nothing and a `run.Warnf` naming the address. `httpsrc.Get` and `GetQuota` return
  only the body of a 200, so the stage calls `ThirdParty.Do` itself to see a referral's status
  and `Location`.
- **Address lookups.** `Checks` yields `ip|<addr>` for each recorded address that is port-eligible
  or in an in-scope netblock, not shared, and not inside an input or ASN-expanded netblock, unless
  a current `registration` record already covers it, and always yields `ip|<asked>` for each
  current `registration` (the address whose lookup produced it, kept in the record). Without the
  second rule `--redo rdap` would yield nothing, sweep every registration and fetch none again. A
  per-run cache in the stage answers later addresses of the same registered range without a
  request. The result is a `registration` record keyed by registry and handle: `start`, `end`,
  `registrant`, `registry`, `handle`, `asked`.
- **`ips.csv`** gains `registrant`, `registrant_netblock`, `registry`, filled by a range lookup
  over `registration` records; `owner` is unchanged.
- **Organisation search.** `Checks` yields `org|<org>|<registry>`. A registry without entity
  search completes with nothing and a note. Results are filtered by `orgname.Matches`, capped at
  50 per registry with a truncation warning. Netblocks are `netblock` observations (candidates by
  the existing scope rule, with `org` set); an RDAP range that is not CIDR-aligned is split into
  its CIDRs first, because a netblock key that is not a prefix is never shown; autonomous systems
  are a new entity kind `asn` (key `AS<n>`; `org`, `registrant`, `registry`), which is a
  candidate while the ASN is not an input.
- **Organisation candidates are records, gated on read.** The address lookup that fetches a
  registration also emits a record of a new entity kind `organisation`, keyed by the registrant
  name as the registry gives it. A check answered from the per-run cache emits nothing, so each
  registration is observed by exactly one check. `inventory.RegistrantCandidate(name)` holds the
  rule of behaviour 4: three or more current `registration` ranges name the registrant, no
  recorded address inside them is shared, and no `--org` input matches the name by
  `orgname.Matches`. The record is a candidate only while the rule holds. Otherwise it stays on
  record and is not listed. It is promoted with `--org`.
- **Both kinds join the candidate model as built.** The `candidate-rank` deriver ranks, and
  `candidates.csv` lists, only the candidate-category records of the kinds in
  `kinds.CandidateKinds`, and both show the kind's name as the type. So:
  - the kinds are named `asn` and `organisation`, the two types `candidates.Promote` already
    turns into `--asn` and `--org`;
  - both are appended to `kinds.CandidateKinds`;
  - `Visibility.category` gains a case for each: an `asn` is a candidate unless the ASN is an
    input, and an `organisation` is one while `RegistrantCandidate` holds;
  - the `Visibility` does not know the `--asn` and `--org` inputs today, so `scope.Config` gains
    them;
  - the deriver's `reads` gains `asn`, `organisation` and `registration`. It re-ranks only when a
    kind in `reads` changes, so without them a new candidate of either type would keep no rank.
- **Evidence**: the stage implements `run.Evidencer`. For an organisation check it returns
  (`rdap`, the organisation), so a result is a registrant-family match of the input organisation
  however many registries returned it. For an address check it returns (`rdap`, the asked
  address), so an organisation candidate's evidence count is the number of lookups that returned
  one of its ranges, which is the number of ranges (behaviour 4). The stage name `rdap` is already
  the registrant entry of the family table.
- **A 429 is `ErrQuota`.** The registries are unkeyed, so this is the case `httpsrc.GetQuota`
  covers. Because the stage calls `ThirdParty.Do` itself (see referrals), it wraps `run.ErrQuota`
  for a 429 itself.

## Tests

`internal/cli/rdap_test.go`, with fakes for IANA and the registries:

- An address is looked up at the registry the bootstrap names; a second address in the same range
  costs no request; excluded classes of address are not looked up.
- A referral inside the six is followed; one outside completes with a warning and no data.
- Organisation search: only word-rule matches are kept; 50 per registry with a warning; a registry
  without search completes with a note; netblocks and ASNs are candidates, never in scope.
- A registrant on three ranges becomes an `organisation` candidate; one matching `--org`, or on
  shared addresses, does not. One whose third range is found on a later run appears then.
- `asn` and `organisation` rows carry a rank: `sources` is `rdap`, an organisation's
  `evidence_count` is its range count, and two addresses of one range count once. An `asn` or
  netblock from an `--org` search alone is `medium`. The summary's promote hint reads
  `--asn AS<n>` or `--org '<name>'`. Passing the ASN as `--asn` removes its candidate row.
- A 429 stops the stage and the checks run next time; each lookup happens once and again only with
  `--redo rdap`; `--redo rdap` with two addresses in one range and no `--org` fetches the range again once; the
  bootstrap is fetched once per run; `--passive` runs the stage.

## Carried from built specs

Follow-ups and limits of the specs already built that bear on this one.

- **Family table (Spec 15, follow-up 2).** `rdap` was reserved in the table for this stage and
  matches its name, so no entry changes. Take `rdap` out of the README sentence that lists the
  reserved names.
- **`Evidencer` (Spec 15).** A stage whose check key carries a setting must implement it, or a
  changed setting counts twice. Neither `rdap` key carries one; `Evidencer` is here to name the
  item, and to make three registries answering for one organisation a single pair.
- **The word rule (Spec 15)** is `orgname.Matches(org, name)`. An organisation with no words
  (only legal suffixes, or nothing) matches nothing, so such an `--org` keeps no results.
- **A candidate never ranked has no rank to keep (Spec 15).** A candidate that stops being current
  keeps its last rank. That holds for the two new types without more code.
- **`Kind` is not comparable (Spec 3).** `CandidateKinds` holds `kinds.Named` values: compare
  `Name()`.
- **Column order.** In `ips.csv` the three new columns come after the existing ones and before
  Spec 19's `srv_ports`, as the build-order plan lists them.
- **Console text (Spec 22).** If Spec 22 has merged, "a `--verbose` warning" and "a `--verbose`
  note" in the behaviours are WARN lines, shown without a flag.

Domain RDAP; replacing the Team Cymru owner lookup; bringing anything into scope automatically.

# Implementation

## Develop

The `rdap` stage is `internal/stages/rdap/rdap.go`, registered after `dnsroot`. A check is
`org|<organisation>|<registry>` or `ip|<address>`; `Evidence` returns (`rdap`, the organisation) or
(`rdap`, the address).

- **Address lookups.** `Checks` yields the `--org` checks, then each known address that
  `View.PortEligible` accepts, is not in an in-scope netblock and is not covered by a current
  `registration`. Port eligibility already excludes shared provider infrastructure, excluded addresses
  and unknown owners, so there is no separate shared test. `Run` takes the stage's per-run state
  (below), returns nothing for an address inside a range already found this run, picks the registry
  from the longest matching prefix of IANA's file, and follows a referral by hand (up to three
  hops, only to `https` URLs on the five registries). Any other host, or a fourth referral, is a
  `run.Warnf` naming the address and a completed check with nothing. A 404 completes with nothing.
  The result is a `registration` record keyed `<registry>|<handle>` and an `organisation` record for
  the registrant, which is the entity with the `registrant` role.
- **Per-run state.** `run.PerRun(ctx, key, init)` is new in `internal/run/stage.go`: a value made
  once per `Runner` run and shared by every check and pass, kept in the context that `passes`
  creates. A `sync.OnceValues` on the stage would have lived as long as the process, so the bootstrap
  would have been fetched once per process and a second run in the same process (every test) would
  have reused a stale or failed one. The state holds the bootstrap of each address family, fetched
  lazily (so an IPv4-only engagement never fetches `ipv6.json`), and the ranges found. The stage
  runs one worker (see Simplify), so a second address in a range waits for the first. The 429 is
  `run.ErrQuota`, wrapped by the stage because `ThirdParty.Do` is called directly for referrals.
- **Organisation search.** A registry's `search` flag is true for ARIN and APNIC. The search is
  `entities?fn=<first word>*`; entities whose `fn` matches by `orgname.Matches` are kept. APNIC's
  search result carries `networks` and `autnums`; ARIN's does not, so the stage requests
  `entity/<handle>` for each match, and stops at 50 results (a network or an autonomous system,
  before it is split into CIDRs), with a `run.Warnf`. A range is split into CIDRs by
  `input.RangeCIDRs`. Netblocks are `netblock` observations with `org` set, and autonomous systems
  `asn` observations. A registry that does not search completes with a `run.Warnf` and no request.
- **Kinds and visibility.** `registration`, `asn` and `organisation` are in their own files;
  `asn` and `organisation` are appended to `CandidateKinds`. `scope.Config` gains `ASNs` and `Orgs`
  (`Scope.HasASN`, `Scope.MatchesOrg`), `BuildScope` passes the inputs, and `Visibility.category`
  and `placement` have a case for each kind. `Inventory.RegistrantCandidate(sc, name)` is the rule
  of behaviour 4 (it counts distinct registration keys, so one netblock seen twice counts once),
  and `Inventory.RegistrationOf` finds the narrowest registered range holding an address for the
  `registrant`, `registrant_netblock` and `registry` columns of `ips.csv`. `registration` joined
  `scopeKinds` and the inventory data; the deriver's `reads` is `scopeKinds` plus `asn` and
  `organisation`.
- **Tests.** `internal/cli/rdap_test.go` drives `cli.Execute` with the real stage against fake IANA
  and registry servers (the fakes answer in ARIN's and APNIC's shapes), one test or more for each
  behaviour: the registry the bootstrap names and one request for a range; excluded classes (input
  netblock, shared, unknown owner, excluded host); referrals inside and outside the six, and a loop;
  the word rule, the 50 cap, a registry without search, an organisation of only legal suffixes;
  three ranges, two addresses in one range, a third range on a later run, an `--org` match and a
  shared address; ranks, `high` with two other families, the promote hints, and an `--asn` input
  removing its row; a 429 and its retry, once per engagement, `--redo rdap` fetching a range once,
  the bootstrap once per run and retried after a failure, and `--passive`. Unit tests cover
  `input.RangeCIDRs`, `Inventory.RegistrationOf` and `RegistrantCandidate`, and the new visibility
  cases. The `rdap` tests failed on their assertions before the stage existed (it was not in the
  registry, so every lookup, row and candidate was missing). `TestRDAP_OrganisationWithNoWordsMatchesNothing`
  passed from the start because nothing searched at all, and now pins that a words-less `--org` keeps nothing.
- **World fakes.** The six hosts are in `sourcePatterns`. `data.iana.org` answers an empty bootstrap
  by default, so a world that does not script it makes no registry request.
- **Deviation: no `ip|<asked>` checks.** The design yielded `ip|<asked>` for each current
  `registration` so that `--redo rdap` would not find every address covered. A redo makes the
  stage's records not current until a completed check observes them again (a record is current only
  while one does), so after a redo no registration covers anything, every address is yielded, and
  the run's own range cache fetches each range once. The extra checks were dead code, and a test
  with the rule removed still passed. `asked` stays in the record, as the address whose lookup
  produced it, and shows in `nyx export`. `TestRDAP_LookupsOnceAndRefreshedByRedo` pins the
  behaviour (two addresses, one range, fetched once) and
  `TestRDAP_AddressInAKnownRangeOnALaterRunCostsNoRequest` pins the covered-address skip.
- **Deviation: which registries search.** The design expected ARIN, RIPE and APNIC to answer
  `entities?fn=` usefully and LACNIC and AFRINIC not to. Checked against the live servers on
  2026-11-15: ARIN and APNIC return an organisation entity that leads to its networks and
  autonomous systems (APNIC in the search result, ARIN at `/entity/<handle>`); RIPE's search returns
  organisation entities with no networks and no link to them; LACNIC answers under `entities` with
  contacts only; AFRINIC answers `entitySearchResults` and returned no organisation for the query
  tried. Only ARIN and APNIC are searched, and the other three complete with a WARN line. RIPE's
  prefixes for an organisation remain `org-asn`'s (RIPEstat).
- **Deviation: the search word.** The search is by the first word of the organisation, with a
  trailing `*`, because a registry's name may add or drop words ("Acme Widgets, Inc." for "Acme
  Widgets Pty Ltd"), and the word rule filters after.
- **Deviation: console text.** The notes of behaviour 1 and 2 are WARN lines (Spec 22 has merged).
  A registry that does not search warns once per organisation and registry, when its check first runs: three WARN lines for each `--org`.
- **Mutation checks.** `## Tests` marks none, so these were spot checks of the riskiest rules, each
  broken by hand and undone by hand, and each failed the test named: dropping the in-scope-netblock
  guard (`TestRDAP_ExcludedClassesAreNotLookedUp`); dropping the port-eligibility test (the same);
  dropping the skip of a covered address (`TestRDAP_AddressInAKnownRangeOnALaterRunCostsNoRequest`);
  dropping the run's range cache (`TestRDAP_AddressLookupAtBootstrapRegistry`,
  `TestRDAP_LookupsOnceAndRefreshedByRedo`); keying the per-run state by a new key each time
  (`TestRDAP_BootstrapOncePerRun`); removing the `ErrQuota` wrap (`TestRDAP_Quota…`); a referral
  hop limit of 100 (`TestRDAP_ReferralLoopStops`); following a referral to any host
  (`TestRDAP_ReferralOutsideTheSixCompletesWithAWarning`); dropping the word rule
  (`TestRDAP_OrganisationSearchKeepsWordRuleMatches`); a cap of 49 or none
  (`TestRDAP_SearchKeepsFiftyPerRegistry`); searching RIPE
  (`TestRDAP_RegistryWithoutSearchCompletesWithANote`); an evidence item that keeps the registry
  (`TestRDAP_RanksAndPromotionHints`); a registrant rule of two netblocks
  (`TestRDAP_ThirdRangeFoundOnALaterRun`); dropping the shared-address rule
  (`TestRDAP_RegistrantMatchingOrgOrOnSharedAddressesIsNotACandidate`); and ignoring an `--asn`
  input in the visibility (`TestRDAP_ASNInputRemovesItsCandidateRow`). The first try at the
  covered-address skip passed, so `TestRDAP_AddressInAKnownRangeOnALaterRunCostsNoRequest` was added.

## Known limitations

- **Behaviour 2: three registries are not searched.** RIPE, LACNIC and AFRINIC return no networks
  for an organisation, so an `--org` finds netblocks and autonomous systems at ARIN and APNIC only
  (RIPE's come from `org-asn`). AFRINIC and LACNIC were each tried with one query; if either adds
  networks to its entities, the `search` flag in the registry table is the one change.
- **Behaviour 2: the search is by the first word.** An organisation whose registered name leaves
  out its first word (the input "The Acme Group" against "Acme Group Pty Ltd") is not found. The
  word rule still decides what is kept.
- **Behaviour 2: ARIN costs a request per match.** Every ARIN entity that matches by name is
  fetched for its networks until 50 results are kept. ARIN's customer entities have none, so an
  organisation name with many customer records costs many requests. Nothing caps the entities
  fetched, only the results kept.
- **Behaviour 3: no IPv6 test.** The bootstrap handling is per family and `RangeCIDRs` has an IPv6
  case, but no behaviour test drives an IPv6 address through the stage.
- **Behaviour 3: a range shown is the narrowest looked up.** The columns of `ips.csv` come from the
  narrowest registration holding the address, so an address looked up through a wider range keeps
  that until a narrower one is looked up. The registries return the most specific range for the
  address they were asked about, so this shows only when a later lookup of another address finds
  a narrower one.
- **Behaviour 4: names are compared exactly.** The same registrant under two spellings
  ("Globex Holdings Ltd" and "Globex Holdings Limited") counts as two registrants, each with fewer
  netblocks.
- **Behaviour 4: `nyx export` and the summary disagree about an organisation.** The export's
  `scope` for an `organisation` record is `candidate` unless an `--org` matches, while the summary
  and `candidates.csv` count it only while the three-netblock rule holds, so the export lists as a
  candidate a registrant the other outputs do not.

## Simplify

Fixed:
- The stage runs its checks with one worker (`Workers` returns 1), which replaces the per-run lock
  and the remembered 429 described under "Per-run state". The runner's own abort test stops the
  next check after a 429, and one worker still makes a second address in a range wait for the first.
- The organisation search and the bootstrap use `httpsrc.GetQuota` instead of a private copy of
  its status mapping. Only `follow`, which needs a referral's status and `Location`, calls
  `ThirdParty.Do` itself.
- `Checks` asks the inventory whether an address is covered (`View.Registered`, which calls
  `Inventory.RegistrationOf`) instead of decoding the `registration` records a second time.
- `inventory.Registration.Contains` is the one range test, used by the inventory and the stage;
  the stage's `span` type is gone.
- `entity` lost its custom `UnmarshalJSON` (a second parse of every entity): whether the answer
  carried networks or autonomous systems is whether either list is non-nil.
- `follow` returns `(body, registry, error)` without a redundant `ok`, its `hostOf` helper is
  inlined, `Run` has one error wrap, and the search's double `truncated` break is a labelled break.
  The registrant role is tested before the vCard is decoded.
- The rank deriver reads `scopeKinds` plus `kinds.CandidateKinds`, so a new candidate kind is
  listed once.
- `Scope.HasASN` dropped a redundant `strings.ToUpper`: the inputs and the stage's keys are already
  `input.ParseASN`'s canonical form.

Skipped:
- Per-registry locks so lookups at different registries overlap: the one-worker form is simpler,
  and lookups are rate-limited per registry anyway.
- Capping ARIN's entity requests per search: a behaviour change, already a follow-up.
- An `organisation` record's placement (`candidate` unless an `--org` matches) differs from its
  summary category (a candidate only while `RegistrantCandidate` holds), so `nyx export` writes
  `candidate` for a registrant the summary does not count. Moving placement and category into a
  per-kind rule is a wider change to `kinds/visibility.go` and changes export output.
- `indexRegistrants` builds its own set of recorded addresses rather than using `KnownAddrs`, which
  needs a scope and leaves out wildcard-only and excluded names. Using it would change which
  registrants count as shared.
- Dropping `RegistrationAttrs.Handle` (it is in the key too): it is a stored attribute and shows in
  `nyx export`.
- A binary search in `RegistrationOf` and a cached `rangeText`, and tokenising `--org` once in the
  scope: a few milliseconds at most at realistic sizes.
- Trimming `TestRDAP_RunsUnderPassiveAndIsRegistered` and deriving the test's registry list from
  its path map: small overlaps in the tests, not worth the churn.

# Verification

## Result

Checked against the code on 2026-11-15. `make test` passes (vet for the four targets, then
`go test -race ./...`) when `$HOME` holds no nyx config: `TestDefaults` in `internal/config` fails
on this machine only because `~/.config/nyx/config.yaml` sets `output_dir`, which this spec does
not touch. `golangci-lint run --new-from-rev=main ./...` reports nothing new.

- **Goal: met, with ARIN and APNIC as the registries that offer organisation search.** `--org`
  now finds netblocks and autonomous systems at ARIN and APNIC as well as RIPE (through `org-asn`),
  registrants of addresses are `registration` records, and related organisations surface as
  `organisation` candidates. Nothing the stage records enters scope: `asn` and `netblock`
  observations from `rdap` are never read by the ASN expansion (it reads only the `asn` stage's
  netblocks for `--asn` inputs), and `registration` records only fill `ips.csv` and the
  registrant rule.
- **B1: met.** `Sources()` is `data.iana.org` and the five registry hosts, so egress refuses any
  other host. An address goes to the longest matching prefix of IANA's file; a referral is
  followed by hand only to `https` URLs on the five registries, at most three hops; a referral or
  bootstrap URL elsewhere completes the check with no data and a WARN line naming the address. The
  README lists the searching registries. The stage is `ThirdParty` and runs under `--passive`.
- **B2: met, for the registries that return an organisation's networks.** The behaviour sends the
  search to "every registry that supports them, which the README lists"; the develop step found
  that only ARIN and APNIC return networks and autonomous systems for an organisation, and the
  README says so. RIPE, LACNIC and AFRINIC complete with no results and a WARN line. The word rule
  is `orgname.Matches`, results are capped at 50 per registry with a WARN line, non-aligned
  ranges are split into CIDRs, and netblocks and ASNs are candidates with source `rdap`. The
  first-word search is a real gap but narrower than `## Known limitations` says: its example ("The
  Acme Group" against "Acme Group Pty Ltd") is rejected by the word rule anyway, since the name
  lacks "the". What the search misses is a registered name that contains every word but does not
  start with the first one ("Acme Widgets" against "The Acme Widgets Company"), because `fn=acme*`
  is a prefix search.
- **B3: met.** `Checks` yields an address only when it is port-eligible (which already excludes
  shared, excluded and unknown-owner addresses), not inside an in-scope netblock (the input and
  ASN-expanded netblocks are the only ones in scope) and not covered by a current registration.
  The per-run cache answers a second address of a range without a request. `ips.csv` keeps `owner`
  and appends `registrant`, `registrant_netblock` and `registry` before the metadata columns.
- **B4: met.** `Inventory.RegistrantCandidate` counts distinct registration keys, rejects a
  registrant with a shared recorded address inside any of its ranges or a name an `--org` matches,
  and `Visibility.category` lists the `organisation` record only while it holds. Its
  `evidence_count` is the number of address lookups that fetched one of its ranges, which is the
  range count (`TestRDAP_RegistrantOnThreeRangesIsACandidate`). `candidates.csv` and the README
  carry the `asn` and `organisation` types, and the promote hints are `--asn` and `--org`.
- **B5: met.** A 429 from a registry (through `follow`) or from IANA and a search (through
  `httpsrc.GetQuota`) is `run.ErrQuota`, which aborts the stage; one worker means no check sends
  after it.
- **B6: met.** Check keys carry no setting, a completed check is not run again, and `--redo rdap`
  makes every address eligible again with the per-run cache keeping it to one request per range.
  `run.PerRun` keeps the bootstrap per run (per family) and a failed fetch fails that run's checks
  only.

Changed while verifying:

- **The spec file itself** had a second copy of the design (from `## Decisions` to
  `## Out of scope`) pasted inside `# Implementation`, ahead of the real `## Develop`. The copy is
  removed, and the "Per-run state" bullet of `## Develop` keeps the text written after Simplify
  (one worker, no lock).
- **An autnum range was cut at 10 systems without a warning (B2).** `results` took at most ten
  ASNs from one autnum object, outside the 50 cap and with no WARN line. Each system of a range is
  now a result of its own, so the 50 cap and its warning cover it; the `maxASNRange` constant is
  gone. `TestRDAP_ASNRangeCountsTowardTheFifty` pins it (it fails with the old cut).
- **No IPv6 test (B3, a known limitation).** `TestRDAP_IPv6AddressLookup` drives an IPv6 address
  through `ipv6.json`, the lookup and the `ips.csv` columns. It passed first time.

Not changed: the `nyx export` placement of an `organisation` record (`candidate` unless an `--org`
matches) disagrees with `candidates.csv` and the summary, as `## Known limitations` says. No
behaviour of this spec covers the export, and which class a registrant that is not a candidate
should have is a decision for the user (see Follow-ups).

## Code review

`/code-review high --fix` found seven issues and fixed four. All four were kept after checking them
against the spec, and `make test` passes afterwards (with a `$HOME` that holds no nyx config, as
above).

Fixed:
- **A registry range that does not hold the address (B3).** `lookup` accepted any ordered pair of
  ends, so a range of mixed families or one that leaves out the address asked about went into the
  run's cache and a `registration` record, and then answered later addresses (here and, through
  `View.Registered`, on later runs) it says nothing about. Such a range is now rejected with the
  existing "gave no address range" WARN line and records nothing. Verification added an
  `Unmap` of the asked address to the containment test.
- **The 50 cap counted repeats (B2).** A result that only repeats netblocks or ASNs another
  matching entity of the same registry already gave no longer counts toward the 50 or triggers
  the truncation WARN line.
- **`run.PerRun`'s doc** now says `init` runs under the run's shared lock, so it must be quick
  and must not call `PerRun` (no behaviour).
- **`candidateRows`' doc** in `internal/output/candidates.go` names `kinds.CandidateKinds` instead
  of the three old types (no behaviour).

Left unfixed:
- **`organisation` placement versus category in `nyx export`:** already a known limitation, no
  behaviour of this spec covers the export, and a fix needs a class for "on record, not a
  candidate" that does not exist. Listed under Follow-ups.
- **`Inventory.RegistrationOf` is a linear scan per address:** set aside in Simplify; nested
  ranges make a binary search non-trivial, and the cost is small at realistic sizes.
- **The rank deriver's `reads` lists `root`, `hostname` and `netblock` twice:** harmless, and
  appending `kinds.CandidateKinds` keeps a new candidate kind to one edit.
